# MIP — YouTube Ingestion/Transcript Pilot: измерения и вердикт

**Дата:** 11.09.2026
**Тип документа:** завершённый пилот / инженерный вердикт (не production-интеграция)
**Статус:** пилот закрыт, вердикт вынесен, есть один явно незакрытый пункт (см. §7)
**Место хранения кода/сырых данных:** `~/mip/experiments/youtube_pilot/` на srv01 (НЕ синхронизировано в GitHub-синк этого Project — только этот checkpoint-документ). Полный отчёт с пошаговым логом — `experiments/youtube_pilot/REPORT.md` на сервере.

Этот документ — консолидированная и непротиворечивая версия отчёта: в ходе пилота часть ранних выводов (по длительности/масштабу IP-блокировки) была скорректирована по мере поступления новых данных. Здесь сразу зафиксирована финальная, исправленная картина, без промежуточных противоречий, которые остались в пошаговом `REPORT.md` на сервере как аудиторский след.

## 1. Задача и гипотеза

Проверить практичность схемы `channel RSS → video discovery → transcript enrichment → нормализованный текст с таймкодами` на реальных YouTube-каналах, без API-ключа, и вынести инженерный вердикт: GO / GO WITH LIMITATIONS / NO-GO на включение YouTube как полноценного `source_type` в МІП.

Гипотеза: YouTube добавляет ценность для контуров C1-C4 (военно-политические шоу, интервью, брифинги, пропаганда, мілблогерський контент), недоступного через существующие Telegram-web-preview и RSS-коллекторы.

## 2. Методология

- Изолированный пилот, без записи в продовую БД, без изменения collectors/schema/Web UI/cron.
- 15 кандидатов-каналов в 3 категориях: UA official/military/news, RU official/propaganda, RU independent/media — подобраны через WebSearch (актуальный статус на сентябрь 2026) и провалидированы эмпирически.
- Discovery: `https://www.youtube.com/feeds/videos.xml?channel_id=...` — без API-ключа.
- Transcript: `youtube-transcript-api` (основной метод) + `yt-dlp` (cross-check/fallback), обе библиотеки эфемерно через `uv run --with`, без изменения `pyproject.toml`/`uv.lock` основной репы.
- Discovery и transcript acquisition выполнены как два раздельных шага/скрипта — по архитектурному требованию ТЗ.
- Выборка: 23 видео с 12 живых каналов (по 2 на канал, 1 — на почти пустом канале).

## 3. Discovery layer — результат: 12/15 живых (80%)

| Категория | Канал | Статус |
|---|---|---|
| UA official | АрміяInform, МО України, Укрінформ, Суспільне Новини | live, все 15/15 записей в RSS |
| UA military media | Мілітарний, DeepState UA | live, 15/15 |
| RU official/propaganda | RT | live, но «последние» видео в ленте — из 2016 года (лента не свежая) |
| RU official/propaganda | Соловьёв LIVE | резолвится, но всего 1 запись в RSS — фактически мёртв |
| RU official/propaganda | Царьград ТВ | dead (404, согласуется с подтверждённым удалением канала в 2020 г.) |
| RU official/propaganda | МО РФ | dead (`"This channel is not available"`) |
| RU official/propaganda | РИА Новости | dead (`"account terminated for ToS violation"`) |
| RU independent | Настоящее Время, TV Rain, Ходорковский LIVE, Живой Гвоздь | live, 15/15 |

**Находка**: живой/резолвящийся канал ≠ свежий канал (кейс RT) — нужна отдельная проверка свежести последней записи, не только факта существования. У 3 из 12 живых каналов (20%) первый угаданный @handle не сработал — потребовалось точечное уточнение при онбординге, это нормальная разовая операция, не блокер.

**Категориальный вывод**: RU official/propaganda на YouTube структурно скудна — 3 из 5 кандидатов подтверждённо мертвы, 1 почти пуст. Если контуру C4 нужен именно официоз РФ, YouTube — слабый источник для этой категории уже на уровне discovery.

## 4. Transcript layer — результат: 69.6% available (n=23)

| Статус | Кол-во | % |
|---|---|---|
| available | 16 | 69.6% |
| unavailable (автор отключил субтитры) | 3 | 13.0% |
| blocked (IP) | 2 | 8.7% |
| error (RSS отдала ещё не начавшийся стрим как «видео») | 2 | 8.7% |

Без учёта 2 «error» (артефакт discovery-слоя, не транскрипт-слоя) — на 21 реальном видео: **available 76.2%, unavailable 14.3%, blocked 9.5%**.

Ручных (человеком сделанных) субтитров — **0 из 16** доступных. Все — автогенерация YouTube (`is_generated: true`). Реальное качество ASR-текста эмпирически не подтверждено (см. §7 — открытый пункт).

Три чётко типизированных, не фатальных класса отказа — библиотека не падает молча, различает причины (`TranscriptsDisabled`, `VideoUnplayable`, `IpBlocked`).

## 5. Главная находка — IP-блокировка выгрузки контента (скорректированный вывод)

Первичное наблюдение (2/23 видео заблокированы) выглядело как точечный, малозначимый риск. Дальнейшая диагностика дала иную, более серьёзную картину:

- **Блокировка точечная по типу запроса, не по IP целиком.** RSS discovery и yt-dlp metadata-listing (`extract_info`) — не блокируются вообще, работают стабильно на всём протяжении пилота. Блокируется именно **выгрузка содержимого субтитров** — причём одинаково у обоих инструментов (`youtube-transcript-api` и `yt-dlp`-download), что указывает на общий caption-serving бэкенд под обоими.
- **Длительность блокировки — минимум ~49.5 минут без признаков снятия** (проверено в 3 контрольных точках: сразу, через ~5 мин, через ~49.5 мин; непрерывного поллинга не было, верхняя граница не установлена).
- Попытка спот-чека качества ASR-текста на уже ранее успешных видео провалилась целиком (4/4 — блокировка эскалировала на весь набор, включая видео, бывшие `available` часом ранее).

**Следствие**: backoff в духе «подождать и повторить через пару минут» не решает проблему — порядок величины блокировки не секунды, а десятки минут. Для production нужен внешний IP (residential/rotating прокси) именно для слоя выгрузки контента субтитров. Discovery и первичный metadata-скрининг можно смело гонять с IP сервера как есть — этого блок не касается.

## 6. Соответствие 8 архитектурным ограничениям ТЗ

Все 8 соблюдены без исключений: без прямого шортката в pgvector, discovery и transcript acquisition разделены, отказ транскрипта не валит ингестию, существующий 15-мин cron не тронут, collectors/schema/UI/prod не менялись, git-операций не было, ASR/Whisper не использовались (только нативные YouTube-caption), credentials/API-ключи не использовались.

## 7. Открытые вопросы (честно не закрыты в рамках пилота)

- **Качество ASR-текста** (связность, точность на укр/рус военной терминологии) — эмпирически не проверено. Попытка спот-чека упёрлась в ту же блокировку выгрузки контента. Требует повторного захода — либо после снятия блока, либо с другого IP.
- Верхняя граница длительности блокировки не найдена (только нижняя — ≥49.5 мин).
- Снижает ли residential/rotating прокси риск блокировки — не тестировалось.
- Малый размер выборки (n=23, по 2 видео на канал) — приведённые проценты индикативны, не статистически устойчивы на уровне отдельного канала; для доверительной оценки нужно n≈30-50 **на канал**.

## 8. Вердикт

**GO WITH LIMITATIONS — обязательное условие: внешний IP/прокси для слоя выгрузки транскриптов.**

Архитектурно пилот чист (все 8 ограничений соблюдены), базовый success rate приемлем (70-76%), отказы предсказуемы и типизированы, discovery-слой полностью надёжен независимо от статуса прокси. Но production-внедрение без решения по IP-блокировке нецелесообразно — на объёме больше пилотного (23 видео) блокировка воспроизведётся предсказуемо и быстро, и de facto превратит источник в ненадёжный без прокси-митигации. Прямой NO-GO избыточен при таких цифрах; чистый GO без оговорки по блокировке был бы недобросовестным.

## 9. Рекомендации для минимальной production-архитектуры (если решение — двигаться дальше)

- `source_type = 'youtube'` потребует ALTER CHECK constraint (не выполнялось в пилоте — чисто DDL-заметка).
- Discovery — отдельный low-frequency воркер, не 15-минутный цикл; пишет video-occurrence кандидатов.
- Transcript fetch — отдельный воркер, обязательно через внешний прокси на слое выгрузки контента; `transcript_status` — персистентное поле, не блокирующая зависимость ингестии.
- Обязательный pre-filter по `live_status`/`duration` перед вызовом transcript API — иначе регулярно ловим `VideoUnplayable` на ещё не вышедших стримах.
- Rate-limiting/request budget per run — иначе воспроизводим наблюдаемую блокировку уже на первом полноценном прогоне.
- `curl_cffi` (impersonation) + `deno` (JS runtime для yt-dlp) — дешёвые меры снижения детектируемости, не устанавливались в пилоте.
- Downstream — тот же контракт `content_items → item_occurrences`, что и у остальных источников, без исключений.
