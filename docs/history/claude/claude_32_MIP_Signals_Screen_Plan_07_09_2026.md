## Частина 2. Обмеження даних — повний список (не переглядати без нових вимірювань)

1. **Час публікації достовірний, але з поправкою на режим збору.** З кроном раз на 15–30 хв `published_at` можна вважати часом посту з похибкою ±15 хв. Для серпня (запуски раз на 1–2 дні) — ненадійно. **Часову аналітику будуємо тільки на періоді від 01.09.**
2. **Обсяг по днях ≠ активність інфопростору.** 49 матеріалів за 23.08 проти 5838 за 03.09 — це графік роботи збирача. Ніколи не рахувати сплески по сирих `count(*)`; тільки частка/log-odds, або нормування на активні джерела через `collected_at`.
3. **Точний дедуп бачить лише 0.48% тиражування** (161+12+3 матеріалів з >1 джерелом з 36.5k). Копія з припискою каналу стає окремим `content_id`.
4. **Семантичний near-duplicate працює в ~16 разів краще:** на випадковій вибірці 150 матеріалів — 12 (8%) мають сусіда з відстанню <0.10, 58 (39%) — <0.20. Медіана 0.243, p25 0.148. **Поріг треба відкалібрувати очима** (крок 1).
5. **Семантика на рівні claims працює погано** — сусіди якоря стоять на 0.41–0.46 і є загальновійськовою лексикою («Работали средства ПВО»). Рівень аналізу — матеріал, не claim.
6. **`facet_code` порожній**, `routing.decision` на 79% `maybe`, claims покривають ~8% матеріалів за добу — жоден із них не може бути обов'язковим входом для сигналів.
7. **Permalink на пост немає** — тільки адреса каналу. Доказ подаємо цитатою + джерело + час, не посиланням.
8. **`confirmed` не гарантує релевантності** — один пост російського каналу дав 34 claims і отримав `confirmed` у контурі ДШВ.
9. **Мамай/порт 8080 не чіпаємо.** Ніяких DB writes і DDL. Ніяких змін у collectors/routing/segmentation/claims-воркерах. Ніяких commit/push без явного запиту.

## Частина 3. Що робимо: екран «Оперативні сигнали»

Один екран, який відповідає на питання аналітика «що змінилось і куди дивитись». Не 200 claims, а 10–20 карток.

Технічні показники (скільки claims, статуси, відсотки обробки) переїжджають окремо в «Стан системи» — але **не завтра**, завтра їх просто не чіпаємо.

### Тип 1. Хвиля (координоване поширення)
- **Питання аналітика:** №5 (хто вкинув першим і як швидко підхопили), №3 (ворожі наративи).
- **Тригер:** група матеріалів з косинусною відстанню < T (калібрується), ≥3 різних джерела, вікно ≤24 год.
- **Картка:** заголовок (перші ~120 символів найранішого матеріалу) · «N джерел за M хвилин» · хто перший (джерело + час) · хронологія підхоплення · склад простору (скільки RU / UA / інші) · докази (цитати) · застереження «поширення не підтверджує правдивість».
- **Дія аналітика:** побачив координований вкид → перевірив зміст → ескалація або ігнор.
- **Вартість:** один SQL з pgvector + connected components у Python. Секунди–десятки секунд.

### Тип 2. Сплеск теми
- **Питання аналітика:** №4 (аномалія), №3.
- **Тригер:** log-odds зростання частки терміна/біграми у поточному вікні проти попереднього, мінімум 3 документи, окремо по `ua_space` і `ru_space`.
- **Картка:** термін · частка зараз проти раніше (не абсолют!) · скільки документів і джерел · цитати з `term_centered_preview` · застереження про базу розрахунку.
- **Дія:** побачив нову тему → провалився в матеріали.
- **Вартість:** переналаштування `topic_explorer_data.py`. **Гейт: наявність кешу лем.** Без кешу stanza на 10k документів — це години, тому без кешу цей тип завтра пропускаємо.

### Тип 3. Контрольний об'єкт (watchlist)
- **Питання аналітика:** №1 (що нового про наші об'єкти), №2 (розголошення).
- **Тригер:** згадка сутності зі списку спостереження у вікні.
- **Картка:** сутність · скільки згадок · розподіл джерел UA/RU (ворожа згадка про наш об'єкт — окремий пріоритет) · цитати · порівняння з попереднім вікном.
- **Підтип OPSEC (найцінніший):** в одному матеріалі зійшлися сутність зі списку + географічна назва + слова про наслідки/втрати. Це груба v1 на співпадінні ключових слів, без NER — так і позначаємо в картці.
- **Вартість:** ILIKE/tsvector по ~30 патернах на ~10k рядків. Секунди.

## Частина 4. Покроковий план на завтра

### Крок 0 — інвентаризація (5 хв, один запит)

```bash
psql -d mip_dev <<'SQL'
\echo '--- 0.1 чи існують таблиці сигналів/кластерів з дизайну ---'
SELECT table_schema, table_name FROM information_schema.tables

\echo '--- 0.2 де кеш лем (гейт для сплесків тем) ---'

WHERE table_name ILIKE '%lemma%' OR table_name ILIKE '%token%' OR table_name ILIKE '%term%'
ORDER BY table_name;

\echo '--- 0.3 обсяг вікна 48 год ---'
SELECT count(DISTINCT io.content_id) AS materials_48h,
       count(*) AS occurrences_48h,
       count(DISTINCT io.source_id) AS sources_48h
FROM item_occurrences io
WHERE COALESCE(io.published_at, io.collected_at) >= now() - interval '48 hours';

\echo '--- 0.4 повнотекстовий індекс для watchlist ---'

SQL
```

Що вирішується: чи є `signals`/`narrative_clusters` (майже напевно ні → працюємо файловим знімком); чи є кеш лем (визначає, робимо тип 2 завтра чи ні); скільки матеріалів у вікні (визначає час прогону); чи є GIN-індекс під пошук watchlist.

### Крок 1 — калібрування порогу схожості (10 хв)

```bash
psql -d mip_dev <<'SQL'
WITH win AS (
  SELECT DISTINCT io.content_id, e.embedding::vector(1024) AS emb
  FROM item_occurrences io
  JOIN embeddings e ON e.content_id = io.content_id AND e.embedding_model_id = 1
  WHERE COALESCE(io.published_at, io.collected_at) >= now() - interval '48 hours'
),
pairs AS (
  SELECT w.content_id AS a, n.content_id AS b, n.dist
  FROM (SELECT * FROM win ORDER BY random() LIMIT 300) w
  CROSS JOIN LATERAL (
    SELECT e2.content_id, e2.embedding::vector(1024) <=> w.emb AS dist
    FROM embeddings e2
    WHERE e2.embedding_model_id = 1 AND e2.content_id <> w.content_id
    ORDER BY e2.embedding::vector(1024) <=> w.emb
    LIMIT 3
  ) n
)
SELECT round(dist::numeric,2) AS band, count(*) AS n
FROM pairs WHERE dist < 0.35 GROUP BY 1 ORDER BY 1;
SQL
```

Далі — очима подивитись по 3 пари з діапазонів 0.05–0.10, 0.10–0.15, 0.15–0.22 (запит дам зранку, він тривіальний: ті самі пари + `left(text_content, 200)` обох сторін). **Рішення кроку:** одне число `T`. Очікування: десь 0.12–0.18. Якщо на 0.15 пари вже не про одне й те саме — беремо 0.10 і миримося з меншою кількістю карток.

### Крок 2 — детектор хвиль (20 хв)

Скрипт (запускаєш ти, я не маю доступу): читає ребра з БД одним запитом, збирає компоненти зв'язності в Python, лишає групи з ≥3 джерелами, сортує за (кількість джерел ↓, тривалість вікна ↑), друкує топ-20 з хронологією.

Ключовий запит усередині (T підставляється з кроку 1):

```sql
WITH win AS (
  SELECT DISTINCT io.content_id, e.embedding::vector(1024) AS emb
  FROM item_occurrences io
  JOIN embeddings e ON e.content_id = io.content_id AND e.embedding_model_id = 1
  WHERE COALESCE(io.published_at, io.collected_at) >= now() - interval '48 hours'
)
SELECT w.content_id AS a, n.content_id AS b, n.dist
FROM win w
CROSS JOIN LATERAL (
  SELECT e2.content_id, e2.embedding::vector(1024) <=> w.emb AS dist
  FROM embeddings e2
  WHERE e2.embedding_model_id = 1 AND e2.content_id <> w.content_id
  ORDER BY e2.embedding::vector(1024) <=> w.emb
  LIMIT 10
) n
JOIN win w2 ON w2.content_id = n.content_id
WHERE n.dist < %(threshold)s;
```

Оцінка часу: ~3–5k матеріалів у вікні × 10 зондів по HNSW ≈ 10–30 секунд. Якщо вікно виявиться більшим за 10k — звужуємо до 24 год.

Connected components — union-find на 20 рядків, без залежностей (перевіримо спершу, чи є `networkx`; якщо є — беремо його, adopt-before-build).

**Критерій готовності кроку:** отримали ≥5 груп із ≥3 джерелами. Якщо груп нуль — поріг завеликий або хвиль справді немає; тоді дивимось топ-20 груп із 2 джерелами і вирішуємо, чи це взагалі робочий сигнал на нашому обсязі.

## Частина 5. Чого завтра НЕ робимо

- Не викликаємо Мамая і не генеруємо LLM-формулювання карток. Спершу підтверджуємо, що механіка знаходить справжні сигнали; формулювання людською мовою — наступний крок, і вхід у нього буде вже готова група з 5–20 повідомлень.
- Не чіпаємо collectors, routing, segmentation, claims-воркери.
- Не робимо DB writes і DDL.
- Не переписуємо `/theses`, `/materials`, `/`, `/sources`.
- Не переносимо технічні показники в окремий розділ (це після `/signals`).
- Не будуємо семантичну кластеризацію claims — перевірено, на цьому рівні вона не працює.
