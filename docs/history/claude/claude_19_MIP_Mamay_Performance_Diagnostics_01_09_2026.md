# МІП — Mamay (llama.cpp/Vulkan) performance diagnostics — 01.09.2026

> Handoff-нотатка за фактично виміряними результатами. Мета: щоб наступна сесія не переганяла той самий діагностичний марафон заново без нового симптому. Апаратна платформа й базовий launch-конфіг — див. `03_MIP_Server_State_18.08.2026.md` (розділи 2, 20-36, 67-69), тут лише перформанс-діагностика поверх того, що вже задокументовано.

## 1. Контекст задачі

Baseline single-stream decode ~16.5-17.7 tok/s (Q4_K_M, 27B, `-ngl all -c 65536 -fa on`, Vulkan1/RTX 5090 Laptop) — здавалось повільним, тому пройшли послідовну діагностику: GPU power/clock throttling → CUDA vs Vulkan → np/context tuning → concurrency.

## 2. Виміряні результати (усе — реальні прогони на живому сервері, не оцінки)

**Prompt processing (prefill):** ~1070-1140 tok/s solo, НЕ bottleneck.

**Decode (generation), single-stream:** ~15.4-17.7 tok/s, стабільний bottleneck. Розкид між прогонами — шум вимірювання, не регресія; для sizing орієнтир ~17 tok/s.

**GPU power/clock — гіпотезу спростовано:**
- Статичний `nvidia-smi -q -d POWER` під час idle показав P8, це нормально (не показник проблеми, треба дивитись під навантаженням).
- Live-телеметрія під час реального decode: `power.draw` ~82-97 W, стабільно НИЖЧЕ і дефолтного (95 W), і поточного (130 W) power limit — карта фізично не впирається в ліміт, `-pl 175` не мало сенсу пробувати (і не пробували).
- SM clock під час decode ~1000-1260 MHz (проти ~2257 MHz на короткому burst під час compute-bound prefill) — це ОЧІКУВАНА поведінка для batch=1 autoregressive decode (bandwidth-bound, не compute-bound), не баг і не throttling.
- Memory clock during decode коливався між 14001 MHz (P0, повний) і 11001 MHz (P2, ~79%) приблизно 55/45 за часом у первинному замірі.
- **Тест-фікс:** `sudo nvidia-smi -pm 1` (persistence mode) + `sudo nvidia-smi -lmc 14001,14001` (memory clock лок на максимум) — команда підтримується на цьому GPU (усупереч типовому обмеженню на laptop GeForce). Після лока — 100% семплів на 14001 MHz підтверджено.
- **Результат:** decode tok/s НЕ зріс (15.42 tok/s після лока, у межах/нижче попереднього діапазону 17.0-17.7) → mem clock oscillation НЕ була реальним bottleneck. Гіпотезу закрито.
- **Важливо:** `-pm 1` і `-lmc 14001,14001` НЕ переживають перезавантаження сервера. Якщо рішення тримати лок постійно — потрібен окремий systemd-юніт/rc-скрипт, це не зроблено.

**np (parallel slots) tuning:**
- `np=1 -kvu` vs дефолтний `np=4`: single-stream decode tok/s практично не змінюється (17.7 vs 17.0). VRAM менше (21.8 vs 23.1 GB), середній GPU util трохи кращий (61.8% vs 54.1%) на np=1.
- `-c 8192` vs `-c 65536` (обидва np=1): decode latency НЕ покращується, але VRAM economy ~4.5 GiB (17.3 vs 21.8 GB) — контекст варто розмірювати під реальний p95 довжини промпту пайплайна, а не тримати 64K "про запас".

**Concurrency (4 паралельних запити, різні промпти, cache miss на всіх):**
- Per-slot decode tok/s падає до ~6.25 t/s кожен (з ~17 solo) — очікувано, конкуренція за пам'ять.
- Агрегатний throughput: ~21-25 tok/s залежно від методу рахунку (25 = сума per-slot decode-rate, тобто чистий decode-throughput; 21 = total_completion_tokens / повний wall-time запиту, тобто end-to-end з урахуванням prefill-фази, де ще ніхто не генерує). Обидва числа коректні, різна метрика — для capacity planning орієнтуватись на end-to-end (~21), не на чистий decode-rate.
- Latency за документ зростає ~2.7-3x (48.8s vs ~15-30s solo залежно від cache hit).
- **Prefill під конкурентністю деградує сильно і нерівномірно:** найдовший промпт (4225 токенів) — 538-656 tok/s (вдвічі гірше за solo ~1100), короткі промпти — 80-165 tok/s (у 7-13 разів гірше). Prefill — compute-bound, чесно ділиться між слотами, на відміну від decode. Якщо реальні продакшн-запити прилітають одночасно БЕЗ спільного prefix-cache hit — це може з'їсти виграш від паралелізму. Тест робився з різними промптами (cached_tokens=0 у всіх) — НЕ тестувався сценарій зі спільним system prompt і прогрітим кешем під конкурентним навантаженням (ближче до реальної продакшн-картини) — це відкрите питання, не виміряно.

**Prompt cache (LCP-based prefix cache):** працює штатно — повторний system prompt дає `cached_tokens` hit, `prompt_ms` падає з ~3950ms до ~300-400ms на 4225-токенному промпті. Великий безкоштовний виграш, якщо пайплайн перевикористовує один system prompt між викликами (зараз так і є).

**CUDA vs Vulkan backend:** НЕ виміряно. Vulkan обрано свідомо (див. `03_MIP_Server_State`, п. 20-36 — "щоб не чіпати system CUDA/driver"). Системний `nvcc 12.4.131` ймовірно застарий для чесної SM_120 (Blackwell) збірки (Blackwell повноцінно завезли в toolkit десь з 12.6-12.8) — підтверджено, що PyTorch/vLLM використовують власний bundled CUDA runtime cu130, а не системний toolkit, тобто CUDA-стек на карті живий, просто не через `/usr/bin/nvcc`. Якщо колись знадобиться — окремий тестовий build llama.cpp з CUDA backend, НЕ чіпаючи прод-інстанс і НЕ чіпаючи системний CUDA/driver, порівняти tok/s на тому ж fixture. Не зроблено зараз свідомо (інша за обсягом задача, немає гарантованого профіту).

**CPU fallback / Intel iGPU:** не виявлено. `n_gpu_layers=all`, VRAM використання відповідає повній моделі, Intel iGPU (Vulkan0/renderD128) — drm-engine-render близько 0 ns, реального compute на ньому нема.

## 3. Підсумок — що можна вважати закритим без нового симптому

Bottleneck — decode-швидкість ~17 tok/s single-stream, це floor для поточного Vulkan-backend на цьому залізі при batch=1 (пам'ять-bound по своїй природі, не конфігураційна проблема). Дешевого "магічного" параметра не знайдено. Power/clock/thermal throttling — спростовано вимірюванням. np/context tuning — задокументовано, рекомендація: `np=1` для latency-чутливих поодиноких запитів, розглянути помірний `np=2-3` з realistic (спільний prompt, прогрітий кеш) concurrency-тестом, якщо пайплайн реально шле паралельні запити й агрегатний throughput важливіший за latency одного документа. CUDA backend — відкрите питання, не пріоритет без виміряної потреби.

**Без нового симптому/виміряної потреби не переганяти:** GPU power/clock діагностику, np=1 vs np=4 single-stream порівняння, c=8192 vs c=65536 latency-порівняння, prompt-cache smoke-test.

**Відкрито, не виміряно:** concurrency з реалістичним спільним prefix-кешем (замість різних промптів); CUDA backend A/B.
