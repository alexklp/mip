# MIP: Feasibility audit слоя «Наші об'єкти» (C1 canonical objects) — консолидированный чекпоинт

Дата: 11.09.2026
Тип: read-only feasibility audit (не реализация). Полный технический отчёт и сырые JSON-агрегаты — на сервере, `~/mip/experiments/object_audit/` (`REPORT.md`, `coverage_simulation.json`, `match_samples.json`, `fn_candidates.json`, `object_drilldown.json`). Этот документ — сведение результатов для Project docs, источник истины для деталей — REPORT.md на сервере.

## Контекст и цель

Задача: определить по фактическому состоянию БД/DDL/кода (не по старым проектным документам) — можно ли строить минимальный analyst-facing экран мониторинга канонических объектов C1 (ДШВ/подразделения) и их алиасов без архитектурного цирка. Будущий продуктовый вопрос слоя: «Что нового про объекты, которые я мониторю, и где это опубликовано» — фундамент для последующего OPSEC-candidate детектирования (объект + локация + время + чувствительный контекст).

Все проверки выполнены read-only (psql `PAGER=cat`, one-off Python/`psycopg`, `SELECT`-only, без `--write`) в `~/mip/experiments/object_audit/`. Ни одна запись/изменение схемы/collectors/Web/cron не выполнялись.

## Фактическая схема (проверено, не из документов)

- `contour_reference_objects` — канонические объекты (для C1: **28**, подтверждено прямым запросом).
- `contour_reference_entries` — алиасы/семантические прототипы. Дискриминаторы `entry_type`, `match_mode` (`exact`/`both`/`semantic`), `active`.
- `content_contour_assignments` — назначения content → contour/object, discriminated-union CHECK по `evidence_type` (`exact_reference`, `semantic_reference`, `deterministic_rule`, `llm_classification`) — сильный существующий паттерн, расширения не требует.
- `item_occurrences` — per-source/per-publication evidence (`source_id`, `published_at`, `external_ref`, `collected_at`) — именно здесь, а не на уровне `content_id`, живёт различие «паблиш / репост / независимый источник».
- `sources.source_group`/`source_type` — готовые поля для UA/RU и TG/RSS срезов.

Вывод: схема адекватна задаче, доработки DDL под MVP не требуются.

## Ключевая находка: операционный разрыв, не архитектурный

- C1 реестр: **28 объектов, 51 активный алиас**, все `match_mode IN ('exact','both')`, **0 semantic-алиасов** (fallback в схеме есть, но нигде не сконфигурирован). Распределение скошено: 15/28 объектов (54%) — ровно 1 алиас.
- `content_contour_assignments` для `evidence_type='exact_reference'` (объектный линкинг, `contour_assignment_worker.py`): **16 строк, все от 26.08.2026 (окно ~2 часа), с тех пор — ни одной новой записи.** Воркер написан, dry-run подтверждён корректным, но **не стоит в cron**.
- Живой cron-воркер (`contour_classification_worker.py`, каждые 30 мин) — не делает object-level линкинг: 38/38 строк C1 с `evidence_type='llm_classification'` имеют `object_id IS NULL`.

Итог: сегодня таблица назначений для object-level данных C1 — замороженный снэпшот от 26.08, а не live-данные.

## Живой coverage (свежая симуляция exact-alias matching, весь корпус 69 924 content_items)

- 44 матча (content, object), 37 уникальных content_id, 7 (19%) — мультиобъектные.
- Замэтчено 6 из 28 объектов за всю историю; 22 (79%) — ни разу (нельзя однозначно сказать: реально нечего показывать или recall gap).
- 24ч: 8 content / 2 объекта. 7д: 17 content / 4 объекта. UA-space и RSS доминируют над RU-space и Telegram.

Сигнал очень тонкий (в среднем ~8 совпадений в сутки по всему реестру из 28 объектов) — экран должен честно показывать «по большинству объектов сегодня ничего», а не имитировать полноту покрытия.

## Ручная проверка качества (малая выборка, 15 из 44 — не статистическая оценка)

- **True positive**: подтверждено на нескольких примерах (censor.net, espreso.tv — публичные материалы).
- **False positive**: в выборке не найдено. Структурно риск снижен — все алиасы C1 составные фразы, не голые числа.
- **Пограничный кейс, проверенный и закрытый**: алиас «68-ї окремої єгерської бригади» на объекте «68 окрема аеромобільна бригада ім. Довбуша» — по открытым источникам (NV, lb.ua, Wikipedia) подтверждено, что это та же часть под другим историческим обозначением (переформирована з аеромобільної в єгерську, затем включена в ДШВ). Алиас корректен, не ошибка реестра.
- **Подтверждённые false negatives** (прямое наблюдение, не домысел):
  1. Морфология: «7 **корпусу** швидкого реагування» (родительный падеж) не матчится против алиаса в именительном падеже — чистое структурное ограничение exact-matching без нормализации словоформ.
  2. Короткие RU-формы: «77-й аэромобильной бригады всу» и «46-й отдельной аэромобильной бригады» — оба относятся к уже отслеживаемым объектам (у 46-й даже 2 активных алиаса), но не совпали с заведёнными формулировками.
- Корректно НЕ матчатся упоминания чужих формирований (российские ВДВ-части, бригада ССО Беларуси) — это правильное поведение, не баг.

## Семантика unit-of-assignment

- Единица назначения — `content_id` (лексический dedup, `sha256(canonical_text)`, не идентификатор события — принятый архитектурный трейдофф проекта).
- Один content может иметь несколько объектов (подтверждено: 19% замэтченных content).
- Различие «паблиш / репост / независимый источник» — на уровне `item_occurrences`, не `content_id`.
- Двунаправленный риск дедупликации: разные источники с разной формулировкой одной новости → разные `content_id` (событие «размножается»); шаблонно-идентичный текст о разных инцидентах → один `content_id` (событие «теряется»). Нужно явно проговаривать в UI будущего экрана.

## Feasibility drill-down (объект «77 окрема аеромобільна Наддніпрянська бригада»)

Чистыми read-only SQL/join-запросами получены: название + алиасы, 24ч count, distinct источники, time dynamics, RU/UA split, evidence-лента (source + timestamp + external_ref, реальные публичные URL). **Feasibility подтверждена** — никакого ML/embeddings/entity linker для этого не требуется.

## Ответ на ключевой инженерный вопрос

Exact/normalized alias matching **достаточен для MVP** — при условии починки операционного разрыва и точечной чистки алиасов (падежи, короткие RU-формы), без добавления entity linker/LLM/embeddings. Объём данных не создаёт нагрузки, оправдывающей embeddings-инфраструктуру; предлагать её сейчас — сложность без измеренной причины.

## Риски качества данных

1. Нет live-процесса object-level линкинга (главный блокер).
2. Скошенное покрытие алиасами — 54% объектов на одном алиасе.
3. Semantic-fallback в схеме есть, но не задействован — нет второй линии защиты от recall gap.
4. Двунаправленный риск `content_id`-дедупликации — «упоминания» ≠ «публикации» ≠ «события».
5. Очень тонкий сигнал — 79% объектов без единого матча за всю историю, причина не установлена (медиапрофиль vs recall gap).

## Минимальный data contract для будущего экрана

Объект (`object_id`, `canonical_name`) → активность за период (24ч/7д: distinct content, distinct источники, UA/RU split, TG/RSS split) → evidence-лента (`occurrence_id`, `source_id`+`source_group`/`type`, `published_at`, `external_ref`, matched-alias) → флаг multi-object. Вне контракта MVP: локализация на уровне сегмента/цитаты, confidence score, кросс-контентная склейка «одно событие = много публикаций».

## Вердикт

Единственный реальный блокер — операционный: включить уже написанный и dry-run-провалидированный `contour_assignment_worker.py --write` в cron, аналогично существующему расписанию `contour_classification_worker.py`. Не NOT READY (фикс не требует новой разработки), не чистый READY (без фикса экран будет показывать трёхнедельной давности заморозку из 16 строк).

## Рекомендуемый следующий шаг (только рекомендация)

Поставить `contour_assignment_worker.py --write` в расписание, инкрементально по новому контенту. Чистку алиасов и SME-проверку 22 «молчащих» объектов — следующим шагом, после включения live-линкинга, когда будет на чём измерять эффект.
