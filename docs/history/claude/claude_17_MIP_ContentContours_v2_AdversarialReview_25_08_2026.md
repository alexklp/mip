# MIP Content Contours v2 — adversarial review правил assignment (25.08.2026)

Статус: **review-документ, ничего в БД не создано и не изменено.** `content_contour_assignments` не существует, `sources.contour_id` не тронут. Ревью проведено по запросу, без предложения нового стека — всё в рамках PostgreSQL/pgvector/BGE-M3.

Входные данные ревью (зафиксировано дословно, чтобы не додумывать за пользователя):

- 4 контуры: C1 Об'єкти ДШВ ЗСУ, C2 Світовий контекст, C3 Загальнодержавний контекст, C4 Моніторинг ворожих медіа.
- C1: 8/8 exact-alias находок релевантны при manual review; semantic similarity на назви частин даёт много ложных срабатываний на російські частини → semantic object match используется только как diagnostic retrieval, не подтверждение.
- C2: median 0.344 / p90 0.424 / max 0.584; даже на 0.54–0.55 смешаны true (НАТО/допомога) и false (Японія-НАТО, загальні заяви РФ, мирні переговори).
- C3: median 0.357 / p90 0.468 / max 0.695; top-20 виглядає чисто, але domin. одним facet — інші facet не валідовані.
- C4: median 0.398 / p90 0.506 / max 0.657; більшість топу з legacy hostile-source provenance group; плутає напрямок — удари РФ по Україні часто отримують facet `ukrainian_strikes_rf`.
- Предложенные правила: C1 exact-anchor-only; C2 semantic + "independent actor/topic anchor"; C3 per-facet calibration, semantic может быть достаточным после проверки каждого facet; C4 hostile-provenance + semantic topic, либо RF-media/RF-official/hostile-narrative anchor для прочих источников, facet не для определения actor/direction.

## 1. По контурам

### C1 (Об'єкти ДШВ ЗСУ)

Правило само по себе — самое чистое из четырёх: exact anchor решает, semantic — только описательный слой поверх уже найденного объекта. Это правильное разделение entity detection и semantic classification (угол 2) — не смешано.

Но есть две дыры, которые эмпирика 8/8 не закрывает:

- **Recall не измерен, и n=8 ни о чём не говорит.** Ты проверил precision на выборке, которая по построению состоит из alias-хитов — это тавтология ("alias-match точен на том, что нашёл alias-match"), она ничего не говорит про то, сколько реальных упоминаний объектов ДШВ проходят мимо из-за неполной таблицы алиасов (сокращения, разговорные названия, транслитерации, опечатки в источниках). При `requires_restricted_access=true` (это уже зафиксировано в Production Design для контуру 1) пропуск релевантного матеріалу — не косметическая проблема, это дыра в моніторингу чутливого контуру.
- **Нет candidate-статуса для полу-совпадений.** Правило говорит "semantic similarity никогда не назначает C1 сама" — правильно, но не говорит, что происходит с контентом, у которого высокий semantic-score по object facet, но нет alias-match. Если он просто выпадает без следа — теряешь ровно то, что нужно для измерения recall выше, и теряешь потенциальную очередь на ручную проверку / расширение alias-таблицы.

### C2 (Світовий контекст)

Это самое слабое место всей системы, и вот почему: правило дословно — "semantic facet + independent actor/topic anchor => assignment", но что такое "actor/topic anchor" — нигде не определено. Это не правило, это placeholder под правило (угол 3, недостаточное).

Хуже: эмпирика (0.54–0.55 смешивает НАТО/допомога с Японія-НАТО і мирними переговорами) — это **буквально та же картина**, которую мы только что подтвердили на Routing v2 ablation (`claude/16`): широкий semantic-facet по военно-дипломатической тематике не различает "стосується України" от "стосується будь-якої країни", потому что косинусна схожість реагує на лексичний overlap ("НАТО", "переговори", "загроза"), а не на референт. Расширение формулировки прототипа там НЕ решило проблему — стало хуже на свежей выборке (22% шум замість 17%).

Практический вывод: если "actor/topic anchor" в C2 задумывается как ещё один semantic score (второй facet, "усиливающий" первый) — это повторение той же ошибки, только с двумя порогами вместо одного, а не решение. Anchor должен быть **детерминированным** сигналом (exact keyword/NER-список: "Україна", "Зеленський", "ЗСУ", список країн-НАТО-в-контексті-України и т.п.), который либо есть в тексте, либо нет — то есть ровно тот класс сигнала, который в общей архитектуре уже назван приоритетным над semantic ("exact/deterministic signals должны иметь приоритет"). Пока это не сформулировано именно так — правило C2 не готово к реализации, не то что к calibration.

### C3 (Загальнодержавний контекст)

Правило честно признаёт, что данных нет: "сильный semantic signal может быть достаточным только после проверки каждого facet отдельно". Это не правило — это план измерения, и его надо явно так и маркировать (угол 3), а не выдавать за рабочую decision rule. Сейчас, если это реализовать как есть, для facet без калибровки нет заданного поведения — implicit fallback либо "ничего не назначать" (тогда почему facet вообще в системе), либо "назначать по default threshold" (тогда вся оговорка про калибровку — фикция).

Отдельная методологическая дыра: "top-20 выглядит чисто" — это оценка ранжирования (похоже на NDCG на глаз), а не precision/recall на пороге. Facet может быть идеальным в топ-20 и сыпать ложными срабатываниями сразу под порогом отсечения — то же самое, что мы видели в Routing v2: верхние примеры выглядят отлично, шум концентрируется в средней зоне margin/score. Калибровка "по каждому facet отдельно" должна мерить именно зону вокруг предполагаемого порога, а не голову списка.

### C4 (Моніторинг ворожих медіа)

Здесь правило прямо отвечает на угол 2 (не смешивать provenance и semantic) — и это правильный инстинкт: "hostile-source provenance + relevant semantic topic" как совместное условие, явный запрет "facet не использовать как надёжное определение actor/direction". Но два момента требуют уточнения, не критики:

- **"hostile-source provenance" — это что технически?** Судя по формулировке "legacy hostile-source provenance group", похоже, это уже существующий признак на уровне source (возможно, тот же `sources.contour_id=4`, назначенный при онбординге источника). Если так — есть риск круговой логики: источник уже промаркирован как hostile при регистрации, а C4-правило по сути наследует эту метку почти без изменений, добавляя semantic topic как фильтр "про что именно из hostile-потока". Тогда C4 precision будет искусственно высокой (population уже отфильтрована), а измерять реально нужно recall — сколько релевантного контента с hostile-провенансом отсекается semantic-фильтром зря — и то, добавляет ли semantic gate вообще что-то полезное против baseline "просто взять весь контент hostile-источников". Это прямо в угол 5 (что измерить) — нужен ablation semantic-gate vs provenance-only, тем же методом, что мы только что использовали для Routing v2.
- **Direction confusion (`ukrainian_strikes_rf` ловит удари РФ по Україні) — это не проблема калибровки порога, это структурный предел embedding-подхода.** BGE-M3 схожість оцінює тематичну близькість (про що текст), а не хто кого — синтаксичні ролі суб'єкт/об'єкт embedding не кодує надійно на рівні короткого prototype-фрази. Тобто "покращити формулювання facet" тут, скоріш за все, повторить те, що вже сталося з Routing v2 prototype: не звузить, а зсуне шум. Реальне рішення — детермінований сигнал напрямку (порядок згадки акторів, прості patterns "Х вдарив по Y" / NER з залежностями), а не семантичний. Або — тупо і чесно: перейменувати facet так, щоб він не претендував на напрямок ("удари по території України" замість `ukrainian_strikes_rf`, з окремим deterministic-сигналом хто актор).
- Правило про "additional RF-media/RF-official/hostile-narrative anchor" для прочих джерел має ту саму хворобу, що й C2 — не визначено, з чого складається цей anchor.

## 2. Наскрізні спостереження (наскрізно по всіх 4)

**Провенанс/entity/semantic змішані нерівномірно.** C1 розділяє чітко (anchor окремо, facet окремо). C4 намагається розділити, але провенанс-джерело сигналу не уточнено (див. вище) і має ризик circularity. C2 і C3 наразі взагалі не мають окремого deterministic anchor — тобто de facto є чисто semantic-правилами, замаскованими під "semantic + anchor", хоча загальний архітектурний принцип проєкту прямо каже: exact/deterministic має пріоритет над semantic. Це найбільша несистемність у поточному наборі правил — 2 з 4 контурів слідують принципу, 2 — ні (поки anchor не визначено).

**Складність розподілена нерівномірно і не там, де треба.** C1 — просте і достатнє правило, з дірою тільки в моніторингу recall/candidate-черги (не в самому правилі). C2 і C4 — недостатні правила (бракує визначення anchor), а не занадто складні. C3 — це взагалі не правило, а намір виміряти. Тобто проблема цієї версії — не "занадто складно", а "недописано" в трьох з чотирьох контурів.

## 3. Спрощення без втрати точності

Замість чотирьох окремих сформульованих-по-різному правил — одна уніфікована двошарова модель, однакова для всіх контурів, що відрізняється лише тим, які довідники/anchor підставляються:

```
assignment(item, contour) =
    CONFIRMED  if exact_reference_match(item, contour)             -- C1-style anchor
             OR (semantic_score(item, contour) >= validated_threshold(facet)
                 AND deterministic_anchor_present(item, contour))  -- C2/C4-style anchor
    CANDIDATE  if semantic_score(item, contour) >= review_threshold(facet)
                 AND NOT CONFIRMED
    NONE       otherwise
```

Це не новий стек — це один Python worker і один SQL enum-статус. Плюси:

- Однакова логіка для C1–C4 замість чотирьох prose-правил — легше підтримувати і тестувати.
- З'являється CANDIDATE-стан замість мовчазного відкидання — закриває дірку C1 (recall/alias-gap) і дає матеріал для калібрування C3.
- Явно змушує визначити `deterministic_anchor_present` для кожного контуру ДО того, як правило стане production-capable — це саме те, чого зараз бракує в C2 і C4, тепер це не можна пропустити мовчки.
- `validated_threshold(facet)` за визначенням per-facet, не глобальний — закриває претензію C2 ("єдиний cosine threshold явно недостатній") і C3 (per-facet calibration) одним механізмом.

## 4. Мінімальні виміри перед persistent `content_contour_assignments`

По контурах:

- **C1**: recall-вимір — вибірка контенту БЕЗ alias-match, але з ознаками ймовірної релевантності (загальні терміни "аеромобільна", "десантно-штурмова" без прив'язки до конкретної частини, тематичні джерела), manual review на пропущені згадки об'єктів. Без цього твердження "8/8 точність" нічого не каже про повноту покриття чутливого контуру.
- **C2**: визначити конкретний склад "actor/topic anchor" (exact keyword/NER-список навколо України/РФ-в-контексті-України), потім прогнати той самий ablation-метод, що й для Routing v2 (`routing_v2_shadow_run_ablation.py` — вже готовий шаблон): semantic-only vs semantic+anchor на вже зібраній 0.54–0.55 змішаній вибірці, порахувати, скільки конкретно false positives anchor реально прибирає.
- **C3**: per-facet precision/recall на межі передбачуваного порогу (не на топ-20), окрема стратифікована вибірка для кожного facet, включно з тими, що поки не представлені в топ-20. Жоден facet не можна вмикати на assignment, поки для нього немає власного виміру.
- **C4**: (a) ablation provenance-only vs provenance+semantic-gate — чи facet взагалі щось додає понад сирий hostile-source provenance; (b) окремий deterministic-сигнал напрямку (хто актор) або перейменування facet без claim на напрямок; (c) уточнити технічне джерело "hostile-source provenance" (це `sources.contour_id=4` чи окрема ознака) — це технічний факт, який треба перевірити в схемі, не вигадувати.

Наскрізно:

- Перевірити, чи новий контент-рівневий multi-label дизайн не розходиться з існуючим "variant 1, conservative" контрактом у `claim_candidate_scan.py` (`contour_set` як union `contour_id` через `item_occurrences → sources`, пари cross-contour лише за повною диз'юнкцією). Якщо `content_contour_assignments` стає джерелом істини на рівні контенту, а `claim_candidate_scan.py` й далі рахує contour_set через `sources.contour_id` — це два розбіжні визначення "яким контурам належить матеріал" у системі одночасно. Треба або мігрувати цей контракт на нову таблицю, або явно задокументувати, чим джерело-рівневий contour_id і контент-рівневий assignment відрізняються і навіщо існують обидва.
- Мінімальна схема (без нового стеку, чисте розширення поточної DDL):

```sql
CREATE TABLE content_contour_assignments (
    content_id      uuid NOT NULL REFERENCES content(content_id),
    contour_id      smallint NOT NULL REFERENCES contours(contour_id),
    status          text NOT NULL CHECK (status IN ('confirmed','candidate','rejected')),
    method          text NOT NULL CHECK (method IN ('exact_anchor','semantic_anchor','semantic_only','provenance')),
    facet_id        text,               -- какой semantic facet сработал, если применимо
    semantic_score  double precision,   -- сырой cosine, если применимо
    anchor_ref      text,               -- что за exact/deterministic anchor сработал (alias_id, keyword, provenance flag)
    embedding_model_id integer REFERENCES embedding_models(embedding_model_id),
    created_at      timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (content_id, contour_id)
);
```

`facet_id`/`semantic_score`/`anchor_ref` окремими колонками — саме те, що не дає provenance/entity/semantic злитись в одне число, і дає змогу пізніше зробити ablation (як у Routing v2) просто фільтром по `method`.

## 5. Резюме

Готово до production вже зараз реально тільки C1, і навіть там бракує recall-виміру. C4 методологічно правильний за задумом, але має недовизначену гілку і непідтверджену directionality — перед persist треба (a) ablation provenance vs provenance+semantic, (b) вирішити directionality. C2 і C3 у поточному вигляді — це не decision rules, а нотатки про напрямок роботи; жодного з них не можна вмикати на запис у `content_contour_assignments` без визначення anchor (C2) або per-facet калібрування (C3).

Пропозиція спрощення (єдина CONFIRMED/CANDIDATE модель, §3) — не архітектурна революція, просто уніфікує те, що C1 вже робить правильно, і застосовує це до решти трьох замість чотирьох різних формулювань.

Рішення, які потрібні від тебе: (1) чи погоджуєшся з CONFIRMED/CANDIDATE моделлю замість поконтурних prose-правил; (2) що технічно є "hostile-source provenance" для C4 — окрема ознака чи `sources.contour_id`; (3) чи мігрувати `claim_candidate_scan.py` contour_set-контракт на нову таблицю, чи лишати обидва визначення паралельно з документованою різницею.
