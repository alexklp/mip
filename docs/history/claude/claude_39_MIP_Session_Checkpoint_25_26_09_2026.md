## 3. C1 Topics: дві різні причини повільності, одна знайдена й виправлена, друга — ще ні

**Причина №1 (знайдена, виправлена, валідована):** `contour_topics_c1.py --all-objects` (28-34 об'єкти) займав до ~45-62 хв замість очікуваних кількох:
- OMP/OpenBLAS не мали лімітів потоків — stanza/torch брали всі 24 ядра. Ізольований замір: 24 потоки=23.2с, 1 потік=18.5с, 4 потоки=15с на один об'єкт. Фікс: `OMP/OPENBLAS/MKL/NUMEXPR_NUM_THREADS=4` в `ops/run_topics_snapshot_once.sh`.
- `fetch_identity_words()` і `load_topics_nlp_cache()` перераховувались (stanza-лематизація ~500 рядків, повне читання NLP-кешу) **заново на кожен з 28-34 об'єктів**, хоча результат однаковий для всього прогону. Фікс: `@lru_cache(maxsize=1)` на обидві. **Валідація не на слово** — 5 об'єктів без кешу vs з кешем дали побайтово ідентичний результат (`json.dumps` порівняння, без `generated_at`), 61.2с→12.6с.

**Причина №2 (розслідувана, НЕ знайдена, лишається відкритою):** навіть після фіксу №1 один живий цикл зайняв 62 хв — конкретні об'єкти (не корелюючи з обсягом даних: 0-13 публікацій) брали 3-18.5 хвилин. `sar`/`mpstat` підтвердили `%nice` CPU 73-91% саме у ці вікна — щось ІНШЕ на машині з `nice`-пріоритетом конкурує за CPU. Перевірено і **відхилено** послідовно:
- `claim_embedding_worker.py`/`claim_candidate_scan.py` (BGE-M3 на CPU, `~/mip`) — не викликаються жодним cron взагалі.
- `object_assignment_worker.py` — чистий regex+psycopg, без BLAS/torch/nice.
- `contours-live` — коректно виходить через `SKIP: mamay.lock зайнятий` саме у ці вікна (сам не конкурент, ділить лок з claims).

Справжній конкурент не знайдений. Замість продовжувати ручний перебір — додано самодіагностику: якщо один об'єкт будується довше 60с, `contour_topics_c1.py` сам пише в лог `ps -eo pid,pcpu,pmem,comm --sort=-pcpu` (топ-10) + `/proc/loadavg` у момент сповільнення. Наступний випадок сам себе задокументує.

## 4. Паралельна робота з GPT — `/search-lab`, координація без конфліктів

GPT (окрема сесія, той самий сервер/repo) паралельно розробляв `/search-lab` — експериментальну сторінку повнотекстового пошуку по `title`+`text_content` (ILIKE, без урахування регістру, з підсвіткою і пагінацією), без пункту меню, як відповідь на кейс "стаття з рідким словом не знаходиться через Теми/Сигнали, бо їхні індекси — не повнотекстовий пошук по всьому корпусу" (Теми ранжують і обрізають; search_index Сигналів — тільки по eligible-кандидатах).

- Перевірено фактично (не на слово GPT): `git diff web/app.py` показав **лише додавання**, жодного видалення мого коду; всі мої ендпоінти (`signals_search_index`, `fmt_kyiv_precise/span` тощо) на місці; 41→87 тестів зелені після кожної перевірки.
- **Два race condition за день** (GPT/користувач заливали файли через GitHub web UI паралельно з моєю роботою) — обидва рази вирішено безпечно: `git fetch` перед комітом, при відмові push — `git stash` (тільки tracked-зміни GPT, їхні нові untracked файли не торкались) → `git rebase origin/...` мого коміту → `git stash pop` → **звірка md5 diff'а до/після stash** (`16ed3d21...` = `16ed3d21...`, побайтово ідентично) → тести → push. Жодного конфлікту, жодної втраченої роботи.
- Закомічено від імені користувача (GPT не має прямого push): `web/app.py`, `web/static/app.css`, `web/search_pilot.py`, `web/templates/search_lab.html`.
- **Оцінка користі `/search-lab` — відкрите питання, не вирішене.** Сторінка є, працює (`HTTP 200`, потрібна стаття з підсвіткою знаходиться), але чи і як інтегрувати повнотекстовий пошук у продукт (окрема сторінка? частина Сигналів/Тем? тільки для C1?) — рішення попереду.
